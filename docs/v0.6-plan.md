# Version 0.6 Phase 1 Review and Plan

## Scope and evidence labels

This plan starts from the released v0.5.0 baseline and defines a minimal v0.6
scope named **Reliable Weekly Runs & History Integrity**. Phase 1 established
the evidence and design. Phase 2A implements the isolated persistence core in
`src/ai_weekly_agent/storage.py`. Phase 2B adds an explicit mixed publication
history reader. Phase 2C connects both to the normal CLI, adds per-attempt
telemetry, and preserves legacy artifacts as read-only compatibility data. No
prompt, model schema, scoring, threshold, retrieval rule, dependency, or
version metadata changed.

Findings below use three evidence labels:

- **Executed:** reproduced in an isolated temporary directory with production
  persistence and history-loading functions; only API/model boundaries were
  replaced with fakes.
- **Source analysis:** established by reading the current implementation and
  tests, but not reproduced as a complete operating-system failure scenario.
- **Not established:** evidence in this phase is insufficient. These items are
  not claims that the user's real data was damaged.

## Current persistence and history behavior

### Identity and overwrite behavior

**Executed:** two different ranges, `2026-09-01..2026-09-07` and
`2026-09-06..2026-09-12`, both map to `reports/2026-W37.md` because the report
filename contains only the end date's ISO year/week. Their raw ResearchRun and
RunRecord filenames contain the full range and therefore differ.

Without `--overwrite`, an existing report is rejected by `main` before
configuration or Research: the reproduction observed zero configuration calls
and zero Research calls. This request-before-work protection already exists and
must not be presented as a new v0.6 feature.

With `--overwrite`, the second range replaces the shared Markdown path. The
first successful RunRecord still points at that path, but its report no longer
reconciles to the first raw artifact. In the reproduction the history loader
reported `range_mismatch`; only the second run remained reconstructable. This
shows a contract-level collision without asserting that this exact overwrite
occurred in the user's real artifact directory.

### Same-range failed overwrite

**Executed:** an old successful artifact set was created in a temporary root,
then the same range was rerun with `--overwrite`. Results were:

| Injected outcome | Raw after rerun | Report after rerun | RunRecord after rerun | Old success reconstructable |
| --- | --- | --- | --- | --- |
| Research failure before new raw | old raw retained | old report retained | replaced by failed Research record | no |
| Curate failure after new raw | replaced | old report retained | replaced by failed Curate record | no |
| Report generation failure | replaced | old report retained | replaced by failed Report record | no |
| Report save failure | replaced | old report retained | replaced by failed Save record | no |
| `KeyboardInterrupt` during Curate | replaced | old report retained | replaced by interrupted/failed Curate record | no |

For every scenario, the old files that were not replaced still existed. That is
not equivalent to usable successful history: the loader found no successful
RunRecord and returned `unavailable`. A failed attempt and a successful
publication currently share the same date-range RunRecord target.

### Atomicity and concurrency

**Source analysis:** raw JSON, Markdown, and RunRecord saves each use a temporary
file followed by `os.replace`. This provides same-filesystem per-file atomic
visibility in the normal supported environment. There is no commit point across
the three files, so it does not provide artifact-set atomicity.

**Executed:** a deterministic barrier placed between `save_report`'s existence
check and final replacement allowed two no-overwrite writers to the same path to
both report success. The final file was one complete writer's content, not a
partial file, but one successful writer silently replaced the other. This is a
check-then-write race. The reproduction used synchronization, not sleeps.

**Not established:** this phase did not kill a real process at every filesystem
or `fsync` boundary, did not test network filesystems, and did not run two full
paid pipelines concurrently. It therefore does not establish crash durability
on every filesystem or prove that a real concurrent weekly run has occurred.

### RunRecord responsibility

The current RunRecord serves two roles: operational attempt telemetry and the
success record required to discover published history. Replacing it with a
failed-attempt record preserves failure observability but removes the success
authority required by the history loader. Existing tests correctly preserve the
best-effort rule: failure to save telemetry must not turn a successfully saved
report into a pipeline failure or replace the primary pipeline error.

Version 0.6 should separate these roles. A small publication manifest should
represent the committed successful artifact set. A per-attempt RunRecord should
represent success/failure observability and remain best effort. Telemetry save
failure must not invalidate a committed report.

## Minimal v0.6 design

### Alternatives considered

1. **Only add the full range to the report filename.** This prevents same-week
   report collisions but does not keep a failed same-range overwrite from
   replacing raw data and the successful RunRecord.
2. **Stage and then replace the three fixed canonical files.** This reduces
   early mutation but still has no atomic three-file replacement. A crash during
   promotion can mix old and new files.
3. **Immutable attempt artifacts plus one atomic publication manifest.** This
   is the smallest option that addresses range identity, failed reruns,
   cross-file consistency, concurrency, and history discovery together. It is
   recommended.

The recommendation uses a lightweight `run_id` only to make an attempt's files
immutable and unambiguous. It is not a database, scheduler, orchestration
framework, analytics system, or general run-management platform.

### Proposed layout

For range `<start>_to_<end>` and content-neutral unique `<run_id>`:

```text
data/raw/<start>_to_<end>/<run_id>.json
reports/<start>_to_<end>/<run_id>.md
data/runs/attempts/<start>_to_<end>/<run_id>/
data/runs/published/<start>_to_<end>.json
data/runs/locks/<start>_to_<end>.lock
```

Phase 2A deliberately reserves an attempt directory rather than an attempt
RunRecord filename. Creating that directory with `exist_ok=False` is the
collision-resistant allocation step; it prevents a reused `run_id` before raw
or report creation. Phase 2C stores the one final per-attempt RunRecord at
`data/runs/attempts/<range>/<run_id>/run.json` using exclusive creation.

The publication file is a small, separately versioned manifest. Schema version
1 contains exactly: `schema_version`, an exact `date_range` (`start`, `end`),
`run_id`, `application_version`, UTC `published_at`, and `raw` / `report`
references. Each reference contains only its canonical filename, SHA-256 digest,
and byte length. It contains no model text, prompt, source body, secret, token
content, arbitrary absolute path, or free relative path. Artifact paths are
derived from the trusted storage root, range, and strictly validated lowercase
32-hex-character `run_id`.

The attempt RunRecord remains operational telemetry. Failed attempts receive
their own record when best-effort finalization succeeds and can never replace a
publication manifest or another attempt. If RunRecord saving fails, a warning
does not invalidate a successful publication or hide the primary pipeline
exception.

### Phase 2A public storage interface

`PublicationStorage(root)` normalizes one trusted working/storage root and
derives every managed path beneath it. Its implemented public operations are:

- `acquire_lock(date_range)` — return a held, non-blocking exact-range
  `PublicationLock` context manager.
- `allocate_attempt(date_range, lock=..., run_id=...)` — atomically reserve the
  attempt identity and return strictly derived `AttemptPaths`.
- `write_raw(attempt, research_run, lock=...)` — serialize and exclusively
  create the original `ResearchRun`; a mismatched range is rejected.
- `write_report(attempt, markdown, lock=...)` — exclusively create final report
  bytes without replacing an existing artifact.
- `publish(attempt, application_version=..., lock=..., overwrite=...)` — verify
  the complete pair and atomically publish the manifest last.
- `read_publication(date_range)` — return `None` only when the manifest is
  absent; return a `PublishedArtifactSet` with one manifest snapshot and the
  exact authenticated raw/report bytes when valid; raise
  `InvalidPublicationError` when a present publication is invalid.

Every mutation validates that its lock is still held and belongs to the same
normalized root and exact range. `generate_run_id()` uses standard-library
UUID randomness, but exclusivity does not rely on probability: allocation and
file creation reject existing targets.

### Publication flow and `--overwrite`

1. Acquire a non-blocking per-range exclusive lock before configuration or any
   API request. Phase 2C keeps normal CLI preflight and the entire attempt under
   it. In the current WSL/Linux target, `fcntl.flock`
   provides the advisory lock without a dependency and the kernel releases it
   on close or process exit. A concurrent cooperating run for the same range
   must fail before paid work; different ranges do not conflict.
2. Under the lock, check the exact range's publication manifest again.
3. Without `--overwrite`, an existing publication for that exact range stops
   the run before configuration/API access. This preserves current preflight
   intent while removing unrelated same-ISO-week conflicts.
4. With `--overwrite`, start one new immutable attempt. Do not mutate the
   currently published set.
5. Save the original raw ResearchRun to the new attempt path before Verify, so
   the audit checkpoint remains real persistence rather than an in-memory mock.
6. Complete Verify, history loading, Curate, Report validation, and immutable
   report saving. Validate both artifacts and their hashes.
7. Atomically replace only the exact range's publication manifest as the final
   commit point. A failed or interrupted run before this point leaves the old
   manifest unchanged. Files from the incomplete attempt are ignored by history.
8. Save attempt telemetry best effort without making the manifest depend on
   telemetry availability. A hard kill may prevent a failure
   RunRecord; v0.6 does not promise observability when the process cannot
   execute cleanup.

For `--overwrite`, success therefore means “publish a new immutable artifact
set for this exact date range and atomically advance its manifest.” It does not
mean replacing another range in the same ISO week. Failure means “retain the
previous manifest and, when possible, write a separate failed-attempt record.”

### Guarantees and limits

- **Single files:** unique artifact files are created without overwriting an
  existing run ID. Phase 2A writes bytes, flushes userspace buffers, `fsync`s
  the artifact file, closes it, and synchronizes its parent directory before
  returning. For publication it creates the manifest temporary file in the
  target directory, writes/flushes/`fsync`s/closes it, performs `os.replace`,
  then synchronizes the manifest directory. This provides atomic manifest
  visibility on the tested local filesystem.
- **Artifact set:** history sees a new set only after the final manifest is
  complete. Hash and strict path checks reject partial, substituted, or unsafe
  sets. This is transactional visibility, not a general filesystem transaction.
- **Concurrency:** the per-range lock prevents two cooperating v0.6 processes
  from spending concurrently or racing the manifest. No guarantee is made
  against external programs that ignore the lock and directly edit artifacts.
- **Interruption:** before manifest commit, the previous publication remains
  authoritative; an orphan attempt may remain for audit/manual cleanup. After
  manifest commit, the publication is authoritative even if the process is
  interrupted before printing its final message.
- **Commit errors:** `PublicationCommitError` and
  `PublicationCommitInterrupted` re-read through the real reader while the lock
  remains held and classify the observed state as `published`,
  `not_published`, or `unknown`. A post-replace directory-sync failure reports
  `published` with durability `unconfirmed`; it is not described as a rollback.
- **Portability:** the initial lock contract is the actual Unix/WSL environment.
  Cross-platform locking should not be claimed without a tested implementation.
  Network-filesystem atomicity is outside v0.6 acceptance unless separately
  designed and tested.
- **Power-loss boundary:** file and directory synchronization follows the
  documented order, but Phase 2A has not performed destructive power-cut or
  filesystem-specific durability testing. Atomic visibility does not prove
  durability on every local or network filesystem.
- **Path safety:** roots and existing managed directory components may not be
  symbolic links or non-directories; final files use no-follow opens and must be
  regular files. Structural containment uses path components, not string
  prefixes. This is a cooperative local protocol and does not claim protection
  against a malicious process concurrently replacing directories.

### Compatibility contract

This is intentionally backward-reading, not completely path-compatible:

- Old v0.5 and earlier artifacts remain untouched. The history loader keeps the
  existing exact legacy rule: successful schema-v1 RunRecord plus its strictly
  canonical legacy raw and weekly report paths.
- The Phase 2B mixed reader discovers new v0.6 history only through a canonical
  publication manifest and strictly derived range/run-ID paths with matching
  hashes.
- It combines valid legacy and v0.6 publications, orders them by the
  existing date policy, applies the existing four-run cap, and prefers a valid new
  manifest over legacy data for the exact same range.
- RunRecord schema 1 has one Phase 2C additive optional `publication` object:
  strict `run_id`, `not_published` / `published` / `unknown` state, and a
  durability boolean only for published outcomes. Older current-model records
  without it remain readable. The publication manifest has its own schema
  version 1; compatibility with untested external consumers is not claimed.
- New report filenames and RunRecord locations are a contract change for tools
  that assume `reports/YYYY-Www.md` or one RunRecord per range. That change must
  be documented rather than described as fully compatible.
- There is no automatic migration, fuzzy legacy parsing, arbitrary-path
  fallback, mutable-URL identity shortcut, or rewrite of historical artifacts.

Phase 2C updates `main.py`, `telemetry.py`, and the minimum storage/history

No Research, Verify, Curate, Report prompt/response contract, scoring,

### Acceptance tests

1. Different ranges ending in the same ISO week have distinct manifests and
   storage artifacts. Phase 2B must prove independent story reconstruction.
2. Phase 2C proves exact-range no-overwrite stops before configuration/API
   access, including a legal empty publication.
3. Phase 2A proves raw/report/manifest write failures and pre-replace
   `KeyboardInterrupt` preserve the previous manifest and immutable artifacts.
   Phase 2C covers Research, raw save, Verify, history, Curate, Report
   generation/save, pre-commit failure, and CLI interruption cases while the
   previous publication remains readable.
4. Phase 2A proves a successful storage overwrite advances only the exact-range
   manifest after both new artifacts and hashes validate.
5. Failed and orphan attempts remain separate and are never history coverage.
6. Phase 2C proves telemetry save failure remains best effort and does not
   invalidate a committed report or replace a primary pipeline error.
7. Phase 2A proves, with deterministic multiprocess synchronization, that only
   one cooperating same-range process gets the lock. Phase 2C proves through
   the real CLI entry that the lock loser makes no configuration or API call.
   No sleep-based tests are used.
8. Phase 2B must preserve legacy W36/W37 strict loading; Phase 2A rejects unsafe,
   mismatched, malformed, unsupported, and hash-invalid new manifests.
9. Phase 2B/2C must retain the existing four-run/three-candidate historical caps
   and all 8/7/7/6 logical call paths.
10. The complete suite and both help-only entry points pass with socket and DNS
    blocked and zero observed network attempts.

### Phase 2B/2C precedence fixed by Phase 2A

- A valid new manifest is authoritative and masks legacy artifacts for that
  exact range.
- Only an absent new manifest permits the existing strict legacy path.
- A present invalid or unsupported manifest produces a diagnostic and skips the
  range; it must not silently fall back, repair itself, or scan attempts.
- An unpublished attempt is never history.
- A valid empty report remains a publication and must not resurrect legacy
  stories for the same range.
- A strictly confirmed legacy publication for the exact range must join the
  Phase 2C lock-held no-overwrite preflight.
- Legacy publications with different exact ranges must not be conflated merely
  because their old report names share one ISO week.

Phase 2B implements these precedence rules in the explicit
`load_publication_history()` entry. Phase 2C connects that reader and the exact
legacy preflight to `main.py`; ordinary CLI writes now use immutable attempt
artifacts and manifest publication rather than the conflicting legacy layout.

### Phase 2B history-read contract

`load_publication_history(current_date_range, storage=..., lookback_runs=...)`
uses only the supplied `PublicationStorage.root`. It discovers new publications
from canonical `data/runs/published/<range>.json` names and legacy records only
from top-level `data/runs/*.json`; it never scans attempts recursively. A
canonical manifest filename establishes authority for that exact range before
content is loaded. Valid, invalid, empty, and partially reconcilable manifests
all mask same-range legacy records. Only manifest absence permits the strict
legacy path.

The storage discovery helper is read-only. A missing published directory means
that no new manifests exist. An unsafe or unreadable directory is instead a
`publication_discovery_failed` result and does not silently fall back to all
legacy data. Non-canonical entries produce
`unexpected_publication_filename`; normal dot-prefixed temporary files ending
in `.tmp` are ignored. A canonical filename with malformed, unsupported,
hash-invalid, missing, unsafe, or mismatched content produces one
`invalid_publication` diagnostic for its range. If a manifest disappears after
discovery, `publication_missing_after_discovery` records the race without
legacy fallback. Legacy discovery and content retain their existing diagnostic
codes; `legacy_discovery_failed` denotes an expected top-level enumeration
failure.

For valid publications, history parses the exact authenticated raw/report bytes
returned by `PublicationStorage.read_publication()` and does not reopen their
paths. The existing ResearchRun parser, deterministic Markdown parser, exact
field/source reconciliation, deep-copy behavior, report positions, and partial
story diagnostics are shared with legacy loading. A valid empty publication is
not damage, contributes no `runs_loaded` count, masks legacy, and allows older
ranges to be considered. Bad ranges likewise do not consume the cap. Ordering
uses report range end/start rather than `published_at`; current, same-end, and
future ranges remain excluded while earlier-ending overlaps remain eligible.

Legacy artifact paths retain the old strict interpretation: relative paths are
resolved under the process's existing path semantics and must equal the
canonical paths under the supplied storage root. Phase 2B does not chdir,
relocate, migrate, search for substitutes, or relax containment to accommodate
relative records created under a different working root.

### Phase 2C CLI execution contract

The normal CLI parses and validates arguments before storage initialization.
It then creates exactly one `PublicationStorage(Path.cwd())`, acquires the
non-blocking exact-range lock, and keeps that lock through:

```text
exact-range preflight
-> configuration validation
-> attempt allocation and one base client
-> Research and immutable original-raw save
-> strict Verify
-> load_publication_history with the same storage
-> Curate and Report/local empty rendering
-> immutable report save
-> manifest commit
-> one best-effort attempt RunRecord save
```

Help and argument errors happen before storage, lock, configuration, or client
work. A normal run on a platform without the required `fcntl` behavior fails
explicitly rather than continuing unlocked. A same-range lock contender exits
without waiting or retrying and before configuration, attempt allocation, or
client creation.

Exact-range lock-held preflight uses this table:

| New manifest | Exact legacy authority | `--overwrite` false | `--overwrite` true |
| --- | --- | --- | --- |
| valid, including empty | not consulted | stop before configuration | proceed |
| invalid/unreadable/unsupported | not consulted | fail closed | fail closed |
| absent | one strict valid success, including empty | stop before configuration | proceed |
| absent | related legacy state ambiguous or damaged | fail closed | fail closed |
| absent | no successful authority | proceed | proceed |

Other exact ranges, including a legacy range ending in the same ISO week, do
not block the current range. Failed RunRecords, raw-only/report-only data, and
orphan attempts are not successful publication authority. Transitioning an
exact legacy publication with `--overwrite` creates a new manifest-backed
publication and does not rewrite the legacy files. A present current manifest
always takes precedence afterward.

The per-attempt record is exclusively created at
`data/runs/attempts/<range>/<run_id>/run.json`. Telemetry owns its strict
schema and byte serialization; storage owns the canonical location, lock/run
identity, and exclusive filesystem write. `raw_research_path` and
`report_path` appear only after that attempt actually saved those artifacts.
The optional schema-v1 publication summary is content-free:

- `not_published` carries `durability_confirmed: null` and describes only this
  attempt, not whether an older publication exists.
- `published` carries `true` after the complete implemented synchronization
  sequence or `false` when publication is visible but durability was not
  confirmed.
- `unknown` carries `null` and is never collapsed into `not_published`.

A normal confirmed commit records pipeline `success` and exits 0. A commit
failure before visibility records `failed/save`, `not_published`, and exits 1.
A visible post-replace or directory-sync failure records `failed/save`,
`published/false`, does not roll back, and exits 1. An ambiguous outcome records
`unknown` and exits nonzero. Storage-classified `KeyboardInterrupt` preserves
the observed publication state and exits 130. An expected telemetry-only
construction, serialization, or save failure after a confirmed publication is
only a warning and leaves exit 0; an interrupt after publication may instead
produce exit 130 without rewriting an already-created immutable record.

The runtime `.gitignore` covers nested raw/report attempts, attempt telemetry,
publication manifests, stable lock files, and their temporary files without
ignoring source, tests, documentation, or controlled fixtures. Existing
tracked legacy artifacts remain tracked and are not removed or migrated.

Offline tests use real `main()`, storage, history, Verify, Curate, renderer,
and temporary files while replacing only configuration/SDK transport and
specific fault boundaries. They cover normal 8/7/6-call paths, valid empty
publication, legacy transition, overwrite preservation, failures at every
pipeline/save boundary, commit classifications, best-effort telemetry, and
two forked CLI processes contending on the production lock with deterministic
events/pipes. These tests establish local control flow and persistence
contracts, not live model semantics, HTTP retry counts, or universal filesystem
durability. No Phase 2C live weekly run has been performed.

## Controlled v0.5 live weekly validation plan

This plan is not execution permission.

### Fixed range and history relationship

Use exactly `2026-09-13..2026-09-19`. It is a completed seven-day range fixed
independently of the execution clock. With the artifacts observed in this phase,
the current v0.5 loader should have one usable preceding run
(`2026-09-06..2026-09-12`, 11 stories) and partial history because the W38
report expected for `2026-09-12..2026-09-18` is absent. This must be rechecked
immediately before execution; the expected state is not a substitute for the
actual preflight result.

This range may exercise history-informed Curate assessment, but it is not
guaranteed to retrieve a related candidate, select a `FOLLOW_UP`, or exercise
selected-history rendering. No threshold, history, prompt, or synthetic story
may be altered to force that outcome. If it is not naturally covered, record it
as untested.

### Isolation and entry point

1. Create a fresh temporary working directory outside the repository.
2. Copy the current local `data/raw/`, `data/runs/`, and `reports/` trees into
   that directory as a reviewable snapshot. Do not symlink writable output
   paths back to the repository and do not copy `.env`.
3. Run the installed/current source entry point from the temporary working
   directory with explicit `--start 2026-09-13 --end 2026-09-19`. In v0.5,
   output roots are working-directory-relative, so this isolates writes.
4. Use `PYTHONPATH` or the existing editable installation to reference the
   reviewed repository source. Research, Curate, and Report prompt paths are
   module-root-relative, not working-directory-relative; preflight their exact
   resolved paths and hashes before the request.
5. Preflight `load_config()` without printing the API key: record only key
   presence, the existing configured `OPENAI_MODEL`, retry count, and timeout.
   Do not change the model. `load_dotenv()` discovery from an isolated working
   directory must be confirmed rather than assumed.
6. Record hashes of both the real artifact trees and isolated snapshot before
   execution; after execution verify that only the temporary tree changed.

### Request budget and stopping rules

- Normal non-empty path: at most eight logical Responses calls—six sequential
  Research calls, one Curate call, and one Report call.
- No prepared Curate candidates: six logical calls. Assessed empty selection:
  seven. Any earlier failure stops at the actual lower count; do not rerun to
  obtain a preferred result.
- Each Research request retains the production `web_search` tool limit of four
  processed built-in tool calls. Built-in web-search calls are distinct from
  logical `responses.parse()` calls and from client HTTP attempts.
- Before authorization, require a finite timeout and `OPENAI_MAX_RETRIES=0`, or
  obtain explicit approval for different retry behavior. With retry zero, each
  logical request has at most one SDK HTTP attempt. No manual retry is allowed.
- Capture existing content-free telemetry: logical calls, stage/category,
  response/request IDs if already recorded, usage completeness, tokens where
  supplied, and web-search status counts. Do not infer cost or treat missing
  tokens as zero.
- Stop immediately on configuration mismatch, unexpected prompt/source hash,
  any API/parse/schema error, timeout, provenance failure that aborts the
  pipeline, artifact write outside the temporary root, request/HTTP budget
  breach, or any need to modify code/data. Preserve the first result and do not
  rerun for quality.
