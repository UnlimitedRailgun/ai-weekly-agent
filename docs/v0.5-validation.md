The current `candidate_005` supplied to Curate was:

- title: `Vector Platform information update`;
- organization: `Signal Works`;
- date: `2026-09-17`;
- summary: `Signal Works published information about an update to the Vector Platform.`;
- technical detail: `The available information does not identify whether the update changes shipped behavior.`;
- benchmark: null.

Its sole supplied historical candidate was:

- ID: `history_2026-09-10_to_2026-09-18_story_005`;
- the same generic title and organization;
- date: `2026-09-11`;
- summary: `Signal Works announced an update to the Vector Platform.`;
- technical detail: `The announcement did not establish whether shipped behavior changed.`;
- benchmark: null;
- retrieval signals: `shared_source_url` and `organization_title_terms`.

The frozen reviewer expectation remains `UNCERTAIN`: the shared organization,
product name, generic wording, and mutable URL show a possible relationship but
do not establish that both descriptions refer to the same specific event.

Phase 5B returned a structurally valid `REPEAT`, valid prior ID, no material
change references, no semantic duplicate, and a score of 1.00. Phase 5C added a
general instruction to establish event identity before using `REPEAT`, to use
`UNCERTAIN` when equivalence remains unresolved, to keep quality scoring
separate, and not to invent `FOLLOW_UP` without a valid current-fact reference.
Phase 5D returned the same structurally valid `REPEAT` result and score.

Known limitation:

> A model-assessed `REPEAT` can be structurally valid while semantically
> unsupported. One ambiguous synthetic development case was classified as
> `REPEAT` and suppressed in both evaluated history-enabled runs, including
> after the reviewed prompt clarification.

At the observed score of 1.00, changing only its status to `UNCERTAIN` would
still leave it below the unchanged 3.25 selection threshold. Therefore a
classification/suppression discrepancy was observed, but no otherwise-selected
story was demonstrably lost in this sample. False suppression of useful items
on other inputs remains possible and unmeasured. Low observed scores are not a
general protection against that risk.

## Cumulative implementation review

No new production-code defect was confirmed in Phase 6A. Actual code and tests
confirm the following invariants:

- Main saves the original raw `ResearchRun` before strict current Verify and
  passes only `VerificationResult.accepted_run` to Curate. Local history can add
  comparison context only to those accepted current items; it cannot restore a
  rejected current candidate.
- Main loads history once. Retrieval occurs once inside Curate after hard
  filters and exact current-run deduplication.
- Prior coverage requires reconciliation of a successful schema-v1 RunRecord,
  canonical raw ResearchRun, and canonical Markdown report. Raw-only and
  unselected candidates are not coverage.
- Artifact roots, date-based paths, report structure, identity fields,
  technical/benchmark rendering, and complete normalized source URL sets are
  checked. Legacy raw data and strict source-filtering/report round trips retain
  dedicated coverage.
- The loader uses at most four usable prior runs. Retrieval supplies at most
  three historical candidates per current item. Four runs are not guaranteed
  to equal four calendar weeks.
- `None` or unavailable history uses the dedicated no-history response schema,
  which exposes no historical fields. Complete/partial usable history uses the
  history-enabled contract.
- Historical IDs are validated per current candidate. `FOLLOW_UP` references
  must resolve exactly to the current summary, benchmark field, or indexed
  technical detail; this structural resolution does not prove material change.
- A validated `REPEAT` is removed before semantic duplicate resolution,
  thresholding, deterministic sorting/diversity, and the 12-item cap.
- Historical context is excluded from the Report model payload and rendered
  deterministically for selected `NEW`, `FOLLOW_UP`, and `UNCERTAIN` items.
  `REPEAT` cannot be represented as a selected `CuratedItem` or rendered.
- New reports round-trip through the three-artifact history loader. Source
  filtering preserves the original raw audit artifact while reconciling only
  deterministically rendered, selected facts.
- Content-free history telemetry preserves known-zero versus not-established
  null semantics through success, provider/validation failure, report failure,
  and interruption paths.

Mocked pipeline call-budget coverage remains:

- selected output: 8 logical calls (`6 Research + Curate + Report`);
- all-repeat output: 7 (`6 Research + Curate`);
- assessed ordinary no-selection: 7 (`6 Research + Curate`);
- no prepared Curate candidates: 6 (`6 Research`).

Historical loading and retrieval add no API call. These call counts do not
establish unchanged tokens or cost.

## Compatibility evidence

Current code reads schema-v1 RunRecords without the additive `history` field and
older call records without `research_category`. Legacy raw Source shapes remain
parseable for standalone compatibility, while fresh Main execution still
requires strict provenance.

The forward-direction compatibility test uses a small `ReleasedV04Reader` proxy
whose fields and default Pydantic extra-field behavior were checked against the
local `v0.4.0` source. It confirms that this source-checked proxy ignores the
additive `history` field. It is not execution of an installed v0.4 package and
does not establish compatibility with untested external consumers.

## DRAFT / NOT PUBLISHED — v0.5.0 release-note summary

Version 0.5.0 adds Historical Awareness / Cross-Run Novelty using bounded,
read-only awareness of previously published local reports. It reconciles each
successful RunRecord with its canonical raw and report artifacts, considers at
most four usable prior runs, and retrieves at most three historical candidates
per current story. Continuity is assessed within the existing single Curate
request rather than by adding another model call. Validated historical context
for selected stories is rendered deterministically, and schema-v1 RunRecords
gain optional content-free history telemetry.

Known limitation: continuity for retrieved candidates is model-assessed. A
structurally valid but semantically unsupported `REPEAT` classification occurred
in both evaluated history-enabled runs for one ambiguous synthetic case,
including after prompt clarification. The case was below the selection threshold
in those samples, so no otherwise-selected story was demonstrably lost, but
false suppression on other inputs remains possible and unmeasured. Risk
acceptance for v0.5.0 release preparation has been granted, but the semantic
limitation remains unresolved and publication is not authorized.

Validation boundary: the implementation has comprehensive offline and
socket-blocked regression coverage plus limited synthetic Curate-only live
evaluation. Those live evaluations selected no stories. A live selected-history
rendering path and a full v0.5 Research-to-RunRecord weekly pipeline were not
tested.
